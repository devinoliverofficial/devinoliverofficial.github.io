# Greenroom for iPhone: the cloud-built shell

This folder turns the Greenroom website into an iPhone app **without a Mac that can run Xcode**.
A Mac in GitHub's cloud does the building. Nothing here changes how the website behaves.

- The app is a thin native shell (Capacitor 8) that holds **a copy of the built website inside it**,
  so it works as a real app, not a link to a web page.
- The Xcode project is **made fresh on every run** (`npx cap add ios`) and then customised by one
  readable script, `prepare.sh`. Nothing generated is kept in git.
- The workflow is `.github/workflows/ios-testflight.yml`. It starts **only by hand**
  (`workflow_dispatch`). It has no `pull_request`, `push` or schedule trigger, because the repository
  is public.
- No secret is in any file. Apple's keys live only in GitHub's locked "Secrets" box.

## How to run it

GitHub, this repository, **Actions**, **iOS TestFlight build**, **Run workflow**. (GitHub only shows that button once the
workflow file is on the default branch, `main`, so this branch has to be merged first.) Pick the **branch that holds
the code you want in the app** (normally `main`): the website copy inside the app is built from it. There are two modes:

1. **`check`** (the default). Builds the app on the Mac **without signing and without any Apple key**, and
   proves what is inside it (icon, privacy manifest, the website copy, no service worker). Use this first,
   and any time you change something here. Needs no secrets at all.
2. **`testflight`**. Signs the app and sends it to TestFlight. Needs the secrets below, the bundle ID, and the
   app record in App Store Connect.
   - On the **very first** `testflight` run, tick **create_signing**. That lets fastlane `match` make the
     distribution certificate and the provisioning profile and store them (encrypted) in the private
     certificates repo. On every later run leave it **off**, so match only reads what is already there.

Use **Run workflow** each time (a new run), never "Re-run": the build number is the run number
(`github.run_number`), and Apple refuses an upload whose build number it has already seen. The version is
`1.0.0`.

A run takes roughly 10 to 15 minutes (my estimate). After the upload Apple spends roughly 10 to 40 more
minutes "processing" the build before it appears in TestFlight. The workflow does not wait for that.

The first run with no committed `package-lock.json` installs the pinned versions with `npm install`
and saves the lock file the install made as a run artifact named **package-lock** (kept 14 days). Download it
and commit it as `ios-app/package-lock.json`; from then on the workflow uses `npm ci`.
(It cannot be made here: this Mac has no Node.)

## Secrets and variables

Settings, **Secrets and variables**, **Actions**.

**Secrets** (needed for `testflight` mode only; the workflow lists any that are missing by name, never by value):

| Secret | What it is and where it comes from |
|---|---|
| `APP_STORE_CONNECT_KEY_ID` | The 10-character Key ID in the key's row, App Store Connect, Users and Access, Integrations, App Store Connect API, Team Keys. |
| `APP_STORE_CONNECT_ISSUER_ID` | The Issuer ID at the top of that same page (a long id with dashes). |
| `APP_STORE_CONNECT_KEY` | The **text of the `.p8` file** Apple lets you download once (open it as text; paste everything, the BEGIN and END lines included). Made with access **App Manager**. If Apple says that cannot create certificates, make the key again as **Admin**. |
| `APPLE_TEAM_ID` | The 10-character Team ID, developer.apple.com, Account, Membership details. |
| `MATCH_PASSWORD` | A long passphrase you invent. It encrypts the certificate and profile in the certificates repo. **Keep a copy somewhere safe:** without it the stored certificate cannot be opened (you would make a new one; Apple allows only three Apple Distribution certificates per team). |
| `MATCH_GIT_URL` | The https address of a new, empty, **private** GitHub repository for the certificates, for example `https://github.com/devinoliverofficial/greenroom-certs.git`. Never make this one public. |
| `MATCH_GIT_PRIVATE_KEY` | How fastlane signs in to that private repo: the text of an SSH **deploy key** (private half) that is registered on the certificates repo only, with write access. The Fastfile writes it to a temporary file on the build machine. |

**Variables** (not secret; optional, because the defaults are already right):

| Variable | Default | Notes |
|---|---|---|
| `APP_ID` | `com.greenroomtour.app` | The bundle ID. **It can never change after the first upload.** |
| `APP_NAME` | `Greenroom Live` | The App Store name (30 characters at most). The plain name "Greenroom" is already taken on the App Store. |
| `APP_DISPLAY_NAME` | `Greenroom` | The short name under the icon on the Home Screen. |
| `DAYBAR_PUSH` | `0` | Set to `1` on Oct 22 (Devin: "apply 0198, turn on the bar pushes"; see "The day bar's pushes"): the app asks Apple for push permission (`aps-environment = production`), and the signing step switches Push Notifications on for the app's bundle ID and makes its signing profile again. The day bar extension needs neither. |

## What each Apple step produces (in the order they are needed)

1. **Entity type and Team ID** (Membership details). Gives `APPLE_TEAM_ID`, and says whether the account is an Individual or an Organization.
2. **Accept the latest agreement** (App Store Connect, Business). Without it the New App button does not work.
3. **The App Store Connect API key** (step 3 above). Gives the three `APP_STORE_CONNECT_*` secrets. The `.p8` downloads only once.
4. **The bundle ID registered with Apple.** The lane tries to do this itself (best effort, with the key). If its log says it could not, add it by hand: developer.apple.com, Certificates, Identifiers & Profiles, Identifiers, plus, App IDs, Explicit, `com.greenroomtour.app`. The key must be allowed to; if not, by hand.
5. **The private certificates repo and the three `MATCH_*` secrets.**
6. **The app record in App Store Connect** (Apps, plus, New App): iOS, the name, English (U.S.), the bundle ID from the list, a SKU such as `greenroom-ios-1`. Apple's API has no way to create this, so it is by hand, and it must exist before the first upload. If the account is an Organization there is a Company Name box: type it exactly, it cannot be edited later.
7. **First `testflight` run with create_signing ticked.** Produces the certificate and profile in the certificates repo, the signed `.ipa`, and the upload. (The `.ipa` is not saved anywhere public.)
8. **TestFlight**: install the TestFlight app on the iPhone, add the Apple Account under an **Internal Testing** group in App Store Connect. The build shows up there after Apple finishes processing it (the app's export-compliance question is already answered by the build, so it does not wait on that).

## What the build does (so you can read the log)

1. Picks the newest non-beta **Xcode 26** on the runner (Apple has required Xcode 26 for uploads since 2026-04-28) and stops if it is older.
2. Runs `selftest.sh`, then `python3 build.py` (the same build the website uses; stdlib only, no installs) so `docs/` is fresh, on the runner only.
3. `prepare.sh names`, then `prepare.sh web`: copies `docs/` into `www/` **leaving out** the service worker, the Add-to-Home-Screen helper pages and the old Classic skin, and in that copy only: renames the PDF reader's two `.mjs` files to `.js` (see risks), and adds `capacitor://localhost` next to every `'self'` in the page's Content-Security-Policy.
4. `npm ci` (or `npm install` the first time), `npx cap add ios`, `npx cap sync ios`.
5. `prepare.sh ios`: sets the Info.plist (name under the icon, portrait only, iPhone only, `arm64`, `ITSAppUsesNonExemptEncryption` false, the permission wording, the `greenroom://` scheme), replaces the icon and the launch pictures, adds the privacy manifest, and sets the bundle ID, `1.0.0` and the build number in the Xcode project. `prepare.sh check` then confirms each one (including that `greenroom://` is in the Info.plist as the one URL scheme, and that `cap sync` registered the App, Filesystem and Share plugins) and stops loudly if anything is off.
6. `check` mode: `xcodebuild archive` without signing, then looks inside the archive. `testflight` mode: fastlane `setup_ci`, API key, `match`, manual signing with that profile, `build_app` (export method `app-store`), `upload_to_testflight` with `skip_waiting_for_build_processing`.

Secrets are passed only as `env:` on the two steps that need them, with `set +x`. (Optional hardening once it works: store the secrets in a GitHub Environment limited to the `main` branch, and keep write access to the repository to Devin alone, since anyone who can run a workflow can also change what it does.) Nothing prints a value, and GitHub also masks them. The `.ipa` is never uploaded as a run artifact. The three GitHub-made actions are pinned to exact commits.

## Decisions made (and why)

- **Bundled copy, not a remote address** (`webDir` copy, no `server.url`). Apple 2.5.2 says an app must be self-contained and may not download code that changes what it does; shipping the web files inside the binary avoids the question. It also helps 4.2 (a repackaged website): a bare link to a site is the thing Apple rejects most. No live-update service is used.
- **4.2 is still a real risk.** Phase 1 has only what the website already does (camera and photo picking through the phone's own picker). The plan from the research is to add real native pieces next (push through Apple, native camera, Face ID lock, share sheet, local bus-call alerts) and name them in the review notes.
- **iPhone only, portrait only.** Skips iPad screenshots and the iPad layout. The website is built for a phone held upright.
- **Deployment target iOS 15** (Capacitor's default; Capacitor 8's minimum). The site uses `100dvh`, which needs iOS 15.4 or later; anyone on an earlier 15.x could see height oddities.
- **The real key name** for the export-compliance answer is `ITSAppUsesNonExemptEncryption` (set to false), not the one in the brief (`ITSAppUsesNonEncryptionExempt`, which does not exist).
- **Name under the icon is "Greenroom"**, the store name is "Greenroom Live" (24 characters would be cut off under an icon).
- **Status bar plugin added** (`@capacitor/status-bar`, config only, no code) so the clock is readable.
- **App plugin added** (`@capacitor/app`, official, pinned `8.1.2`, the latest on the Capacitor 8 line, MIT, pure Swift Package, no privacy manifest of its own) so the page can hear the app being opened by `greenroom://plaid-done`. The page reaches it as `window.Capacitor.Plugins.App` (there is no bundler): iOS Capacitor injects that object, with `addListener`, for every plugin listed in `packageClassList` by `npx cap sync`.
- **Safari plus a custom-scheme return, not an in-app login window.** See "Coming back from the bank by itself".
- **File and share plugins added** (`@capacitor/filesystem` pinned `8.1.5` and `@capacitor/share` pinned `8.0.3`, both official, MIT, the latest on the Capacitor 8 line, checked on the npm registry 2026-10-22) so the PDF and the spreadsheet can leave the app. See "Files from the app: PDF and Spreadsheet".
- **Fastlane from the runner image**, not a Gemfile: no install step, one fewer thing to break. The log prints its version. If it is too old, add a `Gemfile` pinning fastlane.
- **`match` over plain Xcode cloud signing**: Apple's own forum shows plain `xcodebuild` cloud signing working once then failing. The first run creates the certificate, later runs only read it (readonly).

## Coming back from the bank by itself (2026-10-19)

Devin: linking his Chase card from the app worked, but "I had to switch back manually, lets fix this".

**How it works.** Tapping **Open Plaid** opens Plaid's Hosted Link page in Safari (Capacitor hands a `target="_blank"` link to the phone's browser). The app now asks the server (the `plaid` function, action `link`) to tell Plaid to send the person back when its window is done: `hosted_link.completion_redirect_uri = "greenroom://plaid-done"`. The app registers the `greenroom` URL scheme (Info.plist `CFBundleURLTypes`, written by `prepare.sh ios`, checked by `prepare.sh check`), so iOS opens Greenroom for that address. The official `@capacitor/app` plugin turns that into an `appUrlOpen` event; `src/app.js` (`listenForPlaidBack`) listens once, and when the address is `greenroom://plaid-done` it runs the same finish step the **I'm done in Plaid** tap runs (`checkPlaid`: ask the server how it went, close the Connect sheet, then the "connected" note and the same next screen). If the server is still a moment behind it asks again every two seconds, eight more times. As a fallback it also looks when the app comes back to the front (the plugin's `resume` and `appStateChange`, beside the page's own `visibilitychange` and `focus`, and the five-second look while the window is out).

**What it does not do.** The address carries no data and proves nothing: being sent back is only a reason to look now, and the server still asks Plaid how the sign-in went. The server honours only that exact address (anything else a phone sends is ignored). Only the iPhone app asks for it and listens for it (`IN_SHELL`); the website and the Home Screen app send no `redirect`, add no listener, and read no different from before. An app without the plugin, or a server that has not been redeployed, is simply as before: the person switches back by hand and the page still finishes the link by itself when they do.

**What Plaid's own docs say** (https://plaid.com/docs/link/hosted-link/ and the `/link/token/create` reference, read 2026-10-19):

- The field is `hosted_link.completion_redirect_uri`, inside the `hosted_link` object of the link-token request: the address Hosted Link sends the person to when the Link flow is over.
- A custom scheme is accepted: any scheme except reserved ones such as `http` or `tel`. It does not need to be registered in the Plaid Dashboard and need not point to a real place. (Plaid's own example has the form `scheme://some-name`, which is what `greenroom://plaid-done` is.)
- Plaid calls it whether the person finished or asked to exit, so it is never treated as proof of success (we ask the server, which asks Plaid, `/link/token/get`).
- **Plaid's recommended iOS route is different from ours.** The docs say to open the Hosted Link URL in an `ASWebAuthenticationSession` (an in-app sign-in sheet) with `hosted_link.is_mobile_app: true`, and then a separate `redirect_uri` that is a Universal Link (an https address on a domain you own) is **required** for banks that use app-to-app sign-in such as Chase. The docs do not describe opening Hosted Link in the phone's Safari, so the Safari path used here is the part Plaid does not document. We do **not** set `is_mobile_app` (that would demand the Universal Link, and Devin has no domain yet), and the Chase sign-in that already worked in Safari is unchanged.
- There is no word in the docs on a "success" page before the redirect, or on what iOS Safari shows when it is sent to a custom scheme.

**What could not be tested here (no phone, no Xcode, no Plaid window):** whether Plaid's page really performs the redirect when it was opened in Safari rather than an `ASWebAuthenticationSession`, and whether iOS Safari opens Greenroom straight away or first asks "Open this page in Greenroom?" (it usually asks for a custom scheme; the sheet's small print tells the person to tap Open). After the return a Safari tab with Plaid's finished page may be left open behind the app. If the return does not happen at all, nothing is worse than before (see above).

**If Safari's prompt or the leftover tab is unwelcome, the two ways up** (neither built, both need a phone test): (a) open Plaid inside the app with `@capacitor/browser` (a Safari sheet over the app with a Done button; the redirect would close it; no Safari prompt, no leftover tab; the Chase app hand-off may behave differently inside a sheet); (b) Plaid's own route, `ASWebAuthenticationSession` plus `is_mobile_app` plus a Universal Link, which needs a domain for Greenroom and a small piece of native Swift that cannot be compiled or tested without Xcode.

## Files from the app: PDF and Spreadsheet (2026-10-22)

Budget History's summary page has two buttons, **PDF** and **Spreadsheet**, for an accountant. On the website the page hands the file to the browser's own share sheet, or downloads it. Inside the app neither exists: the app's web view has no share sheet for files and no Downloads folder, so without help the file went nowhere while the page still said "Saved".

**How it works now.** Inside the app only (`IN_SHELL`, `downloadSummary` and `shellHandOver` in `src/app.js`), the page makes the file as before, then:

1. `@capacitor/filesystem` writes it into the app's own cache folder (`writeFile`, directory `CACHE`, path `exports/<name>.pdf` or `.xlsx`, the bytes as base64: `bytesBase64` in `src/core.js`). Nothing is written anywhere a person or another app can see; iOS clears the cache folder when it needs room.
2. `@capacitor/share` opens the phone's share sheet with that file (`share`, `files: [the file's address]`, the summary's title as the subject for Mail): Save to Files, AirDrop, Mail, Messages and so on.
3. It says "Saved to Files" only when the share sheet reports that the file went to Files. Closing the sheet says nothing. A file that could not be written, or a share sheet that failed, says so. A second tap while the sheet is up does nothing.

The page reaches both plugins as `window.Capacitor.Plugins.Filesystem` and `window.Capacitor.Plugins.Share` (there is no bundler), the same way it reaches the App and DayBar plugins. The website's own way (`handOverFile`) is unchanged and is never used inside the app. Tests: `tools/run_share_tests.js` (the real page code with the two plugins stood in for), `bytesBase64` in `tools/run_core_tests.js`; `prepare.sh check` refuses an app where `cap sync` did not list `FilesystemPlugin` and `SharePlugin`, and `selftest.sh` proves that refusal.

**Why these two, and how they build.** Both are Ionic's own plugins, pinned to exact versions on the Capacitor 8 line (peer `@capacitor/core >= 8.0.0`), with no install scripts. Like `@capacitor/app` they are Swift Packages that `npx cap sync` adds to the app's `CapApp-SPM` package (iOS 15 or newer, Swift tools 5.9). The share plugin needs only Capacitor. The file plugin also brings one Swift Package of its own, Ionic's `ion-ios-filesystem`, pinned in the plugin to exactly `2.0.1` and fetched from GitHub by Xcode during the build (its npm side also installs the small `@capacitor/synapse` helper, plain JavaScript). Nothing here needs a new permission string or a new privacy manifest entry: the file plugin reads file dates, which the app's manifest already declares (`C617.1`), and the share sheet sends nothing anywhere until the person picks a place.

**Not proven yet (no Mac with Xcode here):** that the two plugins compile in the cloud (run a `check` build of this branch before it goes to TestFlight, as was done for `@capacitor/app`), and on the phone: that the share sheet opens with the file named `<tour>-summary.pdf`, and that Save to Files keeps the name.

## The lock-screen day bar (Devin's idea 20; built 2026-10-21/22, not on main yet)

Devin: "when your phone was locked it still showed where we are at in the day based on the day sheet" (and Oct 22, on Doors: "Door should be actually included": Doors is a step, by the clock like the others). A Live Activity on the lock screen (and in the Dynamic Island): the venue and city on top, the step the day is on in big letters (a sound check's band, or "Your set", under it), and a bar filling toward the next step with its name, its time and the time left. A tap opens that day's day sheet (`greenroom://daysheet?tour=...&show=...`). It is ON for everyone on a tour until the person turns it off in the app's Settings > Notifications (Devin, Oct 22: "this notification should be on by default and someone should have to go to settings and notifications to turn it off"); off is remembered on that phone, for that account. iOS does not ask anything when the app puts the bar up itself (Live Activities are allowed for an app until the person switches them off in the iPhone's Settings); a bar the server starts by push while the app is closed comes with Apple's own "Allow / Don't Allow" under it on the lock screen until the person answers once. His rules (Oct 19): the steps follow the day sheet's clock; a step with no time is skipped; Show Ends is the last band's end time; the bar starts at the first time on the sheet (Lobby Call or Load In) and ends at Bus Call (it comes down 15 minutes after). Which steps, when, and the words are `src/core.js` (`dayTimeline`, `dayAt`, `dayBarState`); `src/app.js` picks the show and hands it to the plugin.

**Pieces.** `native/App/DayBarPlugin.swift` (the page's `window.Capacitor.Plugins.DayBar`: `status`, `show`, `end`), `native/App/GreenroomViewController.swift` (registers it; `prepare.sh` points the scene and `Main.storyboard` at it), `native/App/DayBarAttributes.swift` (what one bar carries, compiled into both targets), `native/DayBar/` (the widget extension, bundle ID = the app's plus `.DayBar`, iOS 16.2 or newer). `prepare.sh ios` copies them in, sets `NSSupportsLiveActivities`, files the extension in the project (`tools/edit_xcodeproj.py --add-daybar`), and adds one line to the app's launch (`DayBarLaunch.start()` in `AppDelegate.swift`, see below); `prepare.sh check` and the check build make sure all of it is there. The Fastfile signs the extension with its own profile (made the first time with the existing certificate).

**What it does without the server (as built).** While the app is open it moves the bar on at each step's minute. While the phone is locked the bar fills and its clock counts by themselves, and at the next step's time it moves on by itself ONE step (that step's own words ride along, as the stale view); after that it stays on that step, bar full, until the app is opened, which catches it up. ## Known risks and what could not be tested offline

Nothing here has run on a Mac in the cloud yet. This Mac has no Xcode, no Node and no network access to Apple. What was verified: the YAML parses and every `run:` block passes `bash -n`; the shell scripts run (`selftest.sh` runs the real `prepare.sh` against a made-up project, with `plutil -lint` and `sips` checks); the JSON and the privacy manifest are valid; the Ruby Fastfile is syntactically valid; the three test suites pass; the build output diff is exactly the guards. What is **not** proven, in rough order of how likely each is to need a fix:

1. **Capacitor's real template vs my copy of it.** `prepare.sh` was written from the template's source on GitHub (8.5.3), not from a generated project. If a line is not where it expects, it stops with a `WRONG ...` line or a named error rather than half-editing. The likeliest places are the Xcode project anchors in `tools/edit_xcodeproj.py`.
2. **Fastlane details** (`update_code_signing_settings`, `build_app` export options, `Spaceship::ConnectAPI::BundleId.create`, `upload_to_testflight` with an API key) were written from fastlane's documented behaviour. The research estimates 3 to 8 failed runs before the first clean one; the `check` mode exists so the app-building half is already proven before any Apple key is involved. If the upload itself fails with an `altool` or Transporter error, the runner's fastlane (2.241.0 per the image notes) may be too old for Xcode 26: add a `Gemfile` pinning a newer fastlane and run `bundle exec fastlane beta`, or upload the `.ipa` with Apple's own `xcrun altool --upload-app` (also needs the API key).
3. **The runner image**: `macos-26`, Xcode 26.x, fastlane 2.241.0 and Node are from GitHub's image notes (medium confidence in the research). The Xcode step stops with a plain message if Xcode is older than 26.
4. **The Content-Security-Policy under `capacitor://localhost`.** I could not confirm whether `'self'` matches it, so the app copy names it outright. If the app comes up blank on the phone, look here first.
5. **`.mjs` files.** Capacitor's file server decides the type from the file extension and `.mjs` is not in its table. A JavaScript module with the wrong type will not load, which would break the PDF reader (settlement and rider PDFs). So the app copy renames the two files to `.js` and points `app.js` at them. If this turns out to be unneeded, delete that part of `prepare.sh`.
6. **The Supabase library still loads from jsDelivr at start-up** (`site/backend.js` imports a pinned `@supabase/supabase-js@2.117.3` from `cdn.jsdelivr.net`), and the fonts load from Google Fonts. So the app is not usable fully offline, and Apple could read the library load as downloaded code (2.5.2). A pinned, version-locked library is the common case and usually passes, but the clean fix is to bundle the library into `www/` in CI and point the app copy at it. That was left out of phase 1 on purpose (untestable here, and the first goal is a build on the phone); it is the first follow-up.
7. **The status bar style** is set through the plugin's config; I could not confirm the plugin applies it at launch. If the clock is dark on black, that is the cause (a one-line Info.plist or small code fix).
8. **Plaid.** The website already uses Plaid's hosted page opened from a tap on a link (`target="_blank"`); Capacitor hands that to Safari. Until 2026-10-19 the person switched back by hand and the app finished when it came to the front. Now Plaid is asked to send the person back to `greenroom://plaid-done` and the app hears it (see "Coming back from the bank by itself"). Not proven on a phone: that Plaid performs that redirect from Safari, what iOS Safari shows first, and a cold start (iOS closed Greenroom while Safari was in front; the retained address is delivered when the page starts listening, and the page's start-up look at an open Plaid window also finishes the link). Test with a real bank on the phone before submitting.
9. **Things that may not work inside the app** (the website's behaviour in a web view that has not been run): "Print / save as PDF" (`window.print()`) on the tour closeout, spreadsheet downloads (`<a download>` of a blob) when the share sheet is not offered, and clipboard copy. Each has a fallback in the code, but none was exercised in a web view. Also unconfirmed: the phone's "secure page" features (clipboard, location, the sign-in code's encryption) need the page to count as a secure context; `capacitor://localhost` should, because its host is `localhost`, but I could not check it.
10. **Browser storage**: the sign-in and drafts live in the web view's storage, which the phone can clear when it is very short of space. Fine for phase 1; a native storage plugin is the fix if it ever bites.
11. **Email buttons open the website**, not the app (no Universal Links yet). The code in a "GREENROOM" email still works typed into the app.
12. **Not part of this phase but will matter at submission** (details are in the research): the account type and Apple's financial-app rule (5.1.1(ix), 3.2.1(viii)), the block / report tools for chat and profiles (1.2), a reviewer demo account (2.1), the privacy policy and App Privacy answers matching the privacy manifest, and screenshots.
